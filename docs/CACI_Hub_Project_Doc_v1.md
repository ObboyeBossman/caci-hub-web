## 1. Project Overview

CACI Hub is a web-based church management system built and maintained by Obboye for Christ Apostolic Church International (CACI) Ghana. It provides a central platform for managing the church's membership directory and internal communications.

The system is a single-assembly deployment — built specifically for CACI, not a multi-tenant SaaS product. All data belongs to CACI.

### Core Design Principles

- Simple over complex — ship something real, fast
- One assembly, one deployment. No multi-tenancy in v1
- Two portals in one app — Admin and Member views separated by role
- Super Admin manages via Supabase Dashboard directly — no separate platform portal in v1
- Free infrastructure where possible — Supabase, Vercel, and Cloudflare R2 free tiers

## 2. User Roles

| Role | Scope | Key Permissions |
|------|-------|-----------------|
| Admin | One assembly | Full control of members, groups, broadcasts, and member permissions |
| Member | Self + permitted scope | Own profile, notifications, and broadcasts visible to them. Extended access granted by Admin via `member_permissions` |
| Super Admin | System-wide | Manages the Supabase project directly. Creates first admin account. Recovers soft-deleted members. No UI portal in v1 |

> Super Admin is Obboye's operator role. It is never exposed to CACI staff. In v1, Super Admin work is done directly in the Supabase Dashboard.

## 5. Database Design

Single Supabase project. All data belongs to CACI. RLS policies scope data by user role only — no multi-tenant isolation needed.

### Table Inventory (10 tables)

| Module | Table | Purpose |
|--------|-------|---------|
| Auth | `user_profiles` | Links Supabase Auth user to role (admin / member) |
| Membership | `members` | Core member registry. Soft-delete only — no hard deletes via RLS |
| Membership | `member_permissions` | Named permission grants from Admin to individual members |
| Membership | `groups` | Departments: Choir, Ushers, Youth, etc. Flat list, no nesting |
| Membership | `group_members` | Junction: which members belong to which group |
| Communication | `broadcasts` | One-way admin announcements. In-app only for v1 |
| Communication | `broadcast_recipients` | Junction for member-targeted broadcasts |
| Communication | `notifications` | Per-member inbox. Written by admin only. Member marks as read |
| Audit | `member_audit_log` | Immutable field-level change log for member records |
| Utility | `member_counter` | Single-row counter for membership number generation |

### Membership Number Format

Every member receives a unique number on creation, generated by the `assign_membership_number` trigger:

```
CACI-00001
```

The counter in `member_counter` never decrements. A number once issued is never reused, even after a soft delete.

### Soft Delete Policy

Admin "delete" performs a soft delete only: `deleted_at = now(), is_active = false`. The member row is never physically removed. RLS filters out soft-deleted rows from all queries. Super Admin can recover soft-deleted records directly in the Supabase Dashboard.

### Row Level Security

RLS is enabled on all tables. Two helper functions power all policies:

- `is_admin()` — checks `user_profiles` for `role = 'admin'`
- `has_permission(text)` — checks `member_permissions` for a named grant

No JWT enrichment hook is used. Role is read directly from `user_profiles` on each policy evaluation. Simple and sufficient for a single-assembly deployment.

## 6. Membership Module

### Member Fields

| Field | Notes |
|-------|-------|
| `membership_number` | Auto-assigned. Format: `CACI-00001` |
| `title` | Optional. e.g. Mr, Mrs, Rev, Elder |
| `full_name` | Required |
| `date_of_birth` | Optional |
| `gender` | `male` / `female` |
| `marital_status` | `single` / `married` / `divorced` / `widowed` / `other` |
| `occupation` | Optional |
| `location` | Optional |
| `phone_number` | Unique per assembly |
| `whatsapp_number` | May differ from phone number |
| `membership_status` | `visitor` / `active` / `inactive` |
| `join_date` | Optional |
| `profile_photo_url` | Stored in Supabase Storage |
| `emergency_contact_name` | Optional |
| `emergency_contact_phone` | Optional |
| `emergency_contact_relationship` | e.g. spouse, parent, sibling |

### Member Permissions

Members have no access beyond their own profile by default. Admin grants named permissions individually:

- `members.read` / `members.write`
- `groups.read` / `groups.write`
- `broadcasts.read` / `broadcasts.write`
- `notifications.read`

### Groups

Groups are a flat list — no nesting or hierarchy. Each group has a `messaging_mode`:

- `open` — any group member can send messages
- `restricted` — only the group leader and Admin can send; all others read only

## 7. Communication Module

v1 is in-app only. No SMS, no email, no push notifications — these can be added in v2.

### Broadcasts

One-way announcements from Admin. Members cannot reply. Three targeting modes:

| `targeting_mode` | Who receives it | How it works |
|-----------------|----------------|--------------|
| `assembly` | Entire church | Fan-out at query time — no recipient rows needed |
| `group` | One specific group | `target_group_id` is set |
| `members` | Selected individuals | Rows inserted into `broadcast_recipients` |

Broadcasts may include an optional attachment (image or PDF) stored in Cloudflare R2.

### Notifications

The `notifications` table is a per-member inbox. Written by Admin only. Members can read their own notifications and mark them as read. Linked to the originating broadcast via `broadcast_id`.

## 8. Media Storage

| Content | Provider | Notes |
|---------|----------|-------|
| Profile photos | Supabase Storage | 1 GB free. Small images. Uploaded directly from frontend |
| Broadcast attachments | Cloudflare R2 | 10 GB free. Zero egress. Signed URL via Vercel Edge Function |

### Broadcast Attachment Upload Flow

1. Frontend calls `/api/get-upload-url` with file metadata
2. Edge Function verifies the user is authenticated and is an admin
3. Edge Function returns a signed R2 URL (time-limited)
4. Frontend uploads file directly to R2 using that URL
5. Frontend saves the resulting `attachment_url` to the `broadcasts` row in Supabase

> Supabase never handles broadcast attachment bytes. Only the URL is stored in the database.

## 9. Portal Architecture

One codebase. Two views. Separated by role after login.

| Portal | Path | Access | URL |
|--------|------|--------|-----|
| Login | `index.html` | Both roles. Detects role and redirects | `caci-hub.vercel.app` |
| Admin Portal | `admin/*.html` | Admin only. Bounces member to `/member/` | `caci-hub.vercel.app/admin/` |
| Member Portal | `member/*.html` | Member only. Bounces admin to `/admin/` | `caci-hub.vercel.app/member/` |

The route guard in `auth.js` runs on every page load. It checks the Supabase session and the user's role in `user_profiles`, then redirects if the user is on the wrong portal.

## 11. Post-Migration Checklist

Run `migration_000_caci_v1.sql` on a fresh Supabase project, then complete the following:

- [ ] Create first admin user in Supabase Auth
- [ ] Insert `user_profiles` row: `role = 'admin'`, `is_active = true`
- [ ] Create a `members` row linked to that admin (`auth_user_id = admin uuid`)
- [ ] Log in and verify RLS: admin can see all members
- [ ] Test: create a member → confirm membership number `CACI-00001`
- [ ] Test: soft delete a member → confirm `deleted_at` is set, member disappears
- [ ] Test: member can only see own profile without permissions
- [ ] Configure Supabase Storage bucket: `media` (public read, authenticated write)
- [ ] Set up Cloudflare R2 bucket for broadcast attachments
- [ ] Deploy Vercel Edge Function: `api/get-upload-url.js`
- [ ] Set all environment variables in Vercel project settings
- [ ] Connect GitHub repo to Vercel — verify auto-deploy on push
